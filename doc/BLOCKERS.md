# 阻塞与取舍记录

> 记录「不好实现 / 需要权衡 / 暂时不做」的点，避免后面重复踩。

## B1. 上传、通知、个人中心（设计稿有，后端无接口）

设计稿顶栏有「上传视频」「通知」「个人中心」入口。这三块依赖 **投稿 / 消息中心** 接口，
需要额外的 csrf + wbi 签名与创作者权限，且与「逆向验证台」的目标无关。

- 处理：**入口保留，点击弹 toast「未接入」**，不伪装成可用。
- 若要真做：`/x/vu/web/add/v3`（投稿）、`/x/msgfeed/*`（消息）需要单独逆向一轮。

## B2. 关注 / 点赞 / 投币 / 收藏 是"视觉态"

点赞、投币、收藏、关注都需要 `csrf=bili_jct` + 对应 POST 接口，且**有副作用**（改真实账号数据）。

- 处理：第一期只展示真实计数（`stat.like` / `favorite` / `coin`），按钮不做真实提交。
- 若要做：`/x/web-interface/archive/like`、`/x/v2/view/coin/add`、`/x/v3/fav/resource/deal`、
  `/x/relation/modify`，全部需要 `csrf`；建议做成"显式确认 + 可撤销"。

## B3. 发评论

`/x/v2/reply/add` 需要 csrf + wbi + 设备指纹，且评论内容审核。第一期评论只读。

## B4. 弹幕

`/x/v1/dm/list.so?oid=<cid>` 返回 deflate 压缩的 XML（`<d p="时间,模式,字号,颜色,...">`）。
需要：解压（`zlib.inflateRawSync`）+ XML 解析 + canvas 渲染 + 时间轴同步。

- 处理：第二/四期做，先把数据解出来缓存，渲染层单独一个组件。
- 难点：高密度弹幕（>5000 条）的渲染性能 → 用 canvas 而非 DOM。

## B5. 1080P+ / 4K / HDR 需要大会员

当前登录号 `bili_36555866110` 是 Lv0 普通用户，`fnval=4048` 只给到 1080P（且部分视频 720P）。

- 处理：清晰度选项里 1080P+ / 4K 会请求失败 → 服务端已做"降档到不高于它的最高档"。
- 若要测高码率：换大会员账号扫码登录（`session.json` 会被覆盖）。

## B6. 合流耗时与大文件

`/api/video/prepare` 是**同步阻塞**的（要等 ffmpeg 跑完才返回 URL）。实测 1080P/72MB 约 1–2s，
但若遇到 4K/长视频（>500MB）会明显变慢，前端只能显示"合流中"。

- 处理（已解决）：ffmpeg `-progress pipe:1` 解析 `out_time` 出百分比 + 平滑 `speed` / `eta`，
  前端 loading 态显示进度条；同一 `bvid+q` 30 分钟缓存。
- 实测：620s / 325MB 视频，合流 133s，进度每秒推一次。
- 仍待改进：改成任务队列（关掉页面也能继续跑），以及多清晰度并发合流的限流。

## B7. Electron 壳的几个坑（第三期）

1. **同源**：Electron 里 `file://` 加载 React 会拿不到 `/api`；必须让主进程起本地 HTTP（复用 `server.js`），
   `BrowserWindow.loadURL('http://127.0.0.1:18787/app')`。
2. **Cookie/登录**：`session.json` 由服务端持有，Electron 只需连本地端口，不碰浏览器 Cookie。
3. **极验（短信登录）**：依赖 Chrome 调试端口 9222，Electron 里要改成自己拉起一个带
   `--remote-debugging-port` 的 Chrome 子进程，或改用扫码登录（推荐）。
4. **视频合流**：打包后 `bin/ffmpeg.exe` 需要随 app 分发（约 70MB），或用 `ffmpeg-static`。

## B9. 图片防盗链

`i0.hdslb.com` 对 `Referer: 127.0.0.1` 返回 403 → 全部图片走 `/api/img?u=` 代理（已完成，带内存缓存）。
Electron 里同理，不能直接用 `<img src="https://i0.hdslb.com/...">`。

## B10. 视频直链有有效期

`playurl` 的 `baseUrl` 带 `deadline` 与签名，约 2 小时过期。服务端 `dashCache` 5 分钟 + `audioCache` 30 分钟，
文件落盘后不受影响；但 `**/api/video/stream`（直连模式）** 若长时间播放会 403 → 前端报错需重试。

## B11. 听影 UI 的「音视频识别 / 人声分离」两个工具页

原稿是文件上传 + 假进度条。真实实现需要：
- **ASR**：Whisper（本地 GPU 或云端），本机跑会把风扇拉满 → 未接入
- **上传分离**：需要本地 demucs 或云端额度 → 未接入（Replicate 402）

处理：两个页面改成写明原因，不再假装有进度。视频详情页里的「识别歌曲 / 人声分离」是**真实可用**的（走 bvid，不走上传）。

## B12. 播放器的自动播放策略

`<video>.play()` 在无用户手势时会被浏览器拒绝（`NotAllowedError`）。
听影 UI 里点卡片进详情页算一次手势，通常能自动播放；如果被拒，点一下画面即可。
想彻底免手势：`muted` 自动播放（但会静音，体验差），或 Electron 里关掉该策略。

## B14. 首页「刷新内容不变」

不是 bug，是数据源特性：

- `/x/web-interface/popular` 返回的是 **bilibili 维护的一期热门榜快照**。同页连续两次调用，20 个 bvid 完全一致。
- 原来前端写死 `pn=1`，所以刷新永远是同一批。

已解决：
- 分页：`pn=1/2/3` 实测 **零重叠**，底部「加载更多」逐页追加
- 换一批：走 `/x/web-interface/wbi/index/top/feed/rcmd`（推荐流），`refresh=0/1/2` 三批互不重复

注意：推荐流需要 WBI 签名 + 登录态，未登录时可能返回空（此时前端会提示「推荐流暂时不可用，先看热门」）。
